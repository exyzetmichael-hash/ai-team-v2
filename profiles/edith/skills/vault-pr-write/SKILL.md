# Vault — запись только через Pull Request

Эта инструкция **дополняет**, а не заменяет встроенный скилл `obsidian` (используй его для чтения/поиска/создания текста заметок — `read_file`, `search_files`, `write_file`, `patch`, ровно как он учит). Эта же инструкция описывает, что делать **после** того, как контент заметки готов: как безопасно донести изменение до vault-репозитория.

**Правило без исключений: ты никогда не коммитишь и не пушишь напрямую в `main`/`master`.** Только через ветку и Pull Request. Даже если тебя явно попросят «запиши прямо» — вежливо объясни, что пишешь через PR, и сделай PR. Репозиторий vault, скорее всего, дополнительно защищён правилом ветки на GitHub, запрещающим прямой push в main, — так что прямой push и не пройдёт технически, но правило соблюдай в любом случае, а не полагайся только на защиту репозитория.

## Переменные окружения, которые тебе доступны
- `$OBSIDIAN_VAULT_PATH` — абсолютный путь к локальному клону vault-репозитория (тот же, что использует скилл `obsidian`).
- `$GITHUB_TOKEN` — fine-grained PAT с правами `Contents: write` и `Pull requests: write` **только на репозиторий vault** (не общий токен). Используется для открытия PR через REST API.

## Порядок действий

1. **Убедись, что рабочая копия чистая и свежая**, прежде чем начинать:
   ```bash
   cd "$OBSIDIAN_VAULT_PATH" && git status --short && git pull --ff-only origin main
   ```
   Если `git status` показывает грязное дерево от предыдущей незавершённой попытки — разберись (скорее всего, забытая ветка), не начинай новую работу поверх мусора.

2. **Создай новую ветку** с понятным именем (дата + короткая суть):
   ```bash
   git checkout -b edith/2026-07-24-deadline-notes
   ```

3. **Внеси изменения** через `write_file`/`patch` (как учит скилл `obsidian`), работая **внутри** `$OBSIDIAN_VAULT_PATH`.

4. **Закоммить и запушь ветку** (не main):
   ```bash
   git add -A
   git commit -m "Краткое описание, что и зачем добавлено"
   git push -u origin HEAD
   ```

5. **Открой Pull Request** через GitHub REST API (не нужен отдельный `gh` CLI):
   ```bash
   curl -s -X POST \
     -H "Authorization: Bearer $GITHUB_TOKEN" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/repos/<owner>/<vault-repo>/pulls \
     -d '{
       "title": "Краткий заголовок PR",
       "head": "edith/2026-07-24-deadline-notes",
       "base": "main",
       "body": "Что добавлено и почему. Коротко, по делу."
     }'
   ```
   Подставь реальные `<owner>/<vault-repo>` — они одинаковые для каждого твоего PR, можешь запомнить.

6. **Скажи Михаилу**, что PR открыт, и дай ссылку (она будет в ответе curl, поле `html_url`). Дальше решение — принимать/мержить — за ним. Твоя работа на этом заканчивается; не мержи PR сам, даже если он тривиальный.

## Если PR не нужен — ты только читаешь
Если задача — «найди в vault», «что там написано про X» — это **не** этот скилл, никакой ветки/PR не нужно, просто используй `obsidian`-скилл для чтения. PR — только когда ты **сам** решил, что стоит записать что-то новое, или Михаил явно попросил дополнить vault.

## Частые ошибки, которых нужно избегать
- Не редактируй файлы прямо в `main` ветке — если забыл шаг 2, `git status` в шаге 1 следующего раза это покажет: остановись и разберись, а не коммить поверх.
- Не открывай PR из веток, где нет реальных изменений (`git diff main --stat` перед коммитом — сколько строк реально меняется).
- Один PR — одна тема. Не накапливай несвязанные правки в одну ветку.
