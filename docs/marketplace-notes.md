# Маркетплейс (WB/Ozon) — решения и проверенные факты

Живой документ под сборку маркетплейс-функций в EDITH (~сентябрь 2026). Здесь только то,
что проверено на живом, и принятые архитектурные решения — не план-пожелание.

---

## Архитектура: тулы + скилл внутри EDITH, а не отдельный агент

В старой («офисной») схеме маркетплейсер планировался отдельным профилем `market` со своим
Telegram-ботом — просто потому, что тогда всё было профилями. После перехода на EDITH
(единый ассистент) это пересмотрено: **отдельная личность здесь не нужна.**

Разбор того, что маркетплейсер реально делает:

| Функция | Что это технически |
|---|---|
| читает заказы, остатки, цены | вызовы Seller API = **инструменты** |
| предлагает действия | рассуждение = **сама модель** (EDITH) |
| действует только по явному «да» | **`approvals`** + правило в `SOUL.md` |
| замечает события (упал остаток, новый заказ) | **cron** + проактивное сообщение |

Ни один пункт не требует отдельного бота. Поэтому:
1. **Seller API → инструменты** (MCP-сервер либо Python-тулы в реестре Hermes) — ровно так же,
   как сейчас подключён Todoist.
2. **Экспертиза маркетплейсера → скилл** (`skills/marketplace/SKILL.md`) + раздел в `SOUL.md`,
   по образцу `vault-pr-write`.
3. **Мониторинг → cron**, как утренняя сводка.

**Побочная выгода объединения.** В старой схеме `finance` имел явный запрет лезть в финансы
маркетплейса («это маркетплейсер, когда появится»), и связать «выручка с WB просела, а аренда
через неделю» было физически некому — разная память, разные боты. У EDITH личные деньги и
выручка в одной голове.

⚠️ **Цена решения — токены.** Схемы инструментов уходят в контекст на КАЖДОМ ходу, включая
«поставь напоминание». У WB/Ozon методов много. Обязательно фильтровать список через
`include:` (как уже сделано для Todoist, где из ~45 инструментов оставлено 9), иначе каждое
бытовое сообщение начнёт стоить как маркетплейс-запрос.

## Гео-доступ: прокси НЕ нужен (проверено 2026-07-29)

Роадмап закладывал запасной план: «Seller API WB/Ozon может блокировать EU-адреса → поднять
ру-прокси на AdminVPS и гнать через него только маркетплейс-трафик». **Проверено с боевого
сервера (Contabo, EU) — блокировки нет, план не нужен.**

Замер с Contabo:

| Хост | Результат |
|---|---|
| `api-seller.ozon.ru` | HTTP 401 |
| `content-api.wildberries.ru` | HTTP 401 (connect 0.12s) |
| `marketplace-api.wildberries.ru` | HTTP 401 (connect 0.11s) |
| `statistics-api.wildberries.ru` | HTTP 401 (connect 0.11s) |
| `common-api.wildberries.ru` | HTTP 401 (connect 0.09s) |
| `advert-api.wildberries.ru` | HTTP 401 (connect 0.11s) |
| `feedbacks-api.wildberries.ru` | HTTP 401 (connect 0.05s) |

`401` здесь — правильный результат: «запрос дошёл, нужен ключ». Быстрый connect (0.05–0.12s)
исключает фильтрацию. **Следствие:** российский VPS (AdminVPS) под маркетплейс не требуется —
можно не продлевать, если он держался только ради этого.

Если ситуация изменится (WB/Ozon введут гео-фильтр), архитектуру EDITH это не затронет:
прокси живёт на уровне сетевого доступа тулов, агент о нём не знает.

## ⚠️ Мёртвый домен: `suppliers-api.wildberries.ru`

**Отключён 30 января 2025.** Не использовать ни в коде, ни в тестах. Единый домен разнесён
на отдельные по сервисам (таблица выше).

Как это всплыло: при первой проверке гео-доступа я дал этот хост по памяти, он вернул
`curl: (6) Could not resolve host` — и это легко было принять за блокировку. Диагностика
(DNS → TCP → TLS по отдельности) показала, что имя просто не существует. **Урок тот же, что
с дважды сломанным `office_report`: сверяться с [dev.wildberries.ru](https://dev.wildberries.ru/),
а не с памятью модели.** Особенно здесь — WB меняет API заметно чаще, чем обновляется база
знаний любой LLM.

## Что осталось на сентябрь

- [ ] Ключи продавца WB и Ozon (делает владелец, в личных кабинетах). У WB токен живёт
      180 дней — сразу заложить напоминание на продление, иначе интеграция тихо умрёт.
- [ ] Реализация тулов под реальные данные. **Не писать вслепую до появления ключей** — на
      этом уже обжигались: `office_report` дважды был сломан именно потому, что писался без
      живого прогона.
- [ ] Список методов сверить по актуальной документации на момент написания.
- [ ] `skills/marketplace/SKILL.md` — как EDITH думает про маркетплейс: что считать нормой,
      когда бить тревогу, что никогда не делать без подтверждения.
- [ ] Режим подтверждений: любое изменение цен/остатков/заказов — только после явного «да».
