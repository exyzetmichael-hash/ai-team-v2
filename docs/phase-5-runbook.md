# Фаза 5 — Runbook: офис (агенты видят друг друга)

**Цель:** семь агентов работают как команда. Задачу, которая не по адресу, агент передаёт коллеге сам, без куратора. В общем чате отвечает тот, кому тема ближе.

Это **две независимые части**. Часть 1 (Kanban) — готовая функция Hermes, ничего от тебя не требует кроме конфигов, и работает сразу. Часть 2 (общий чат) требует завести шесть новых ботов и содержит единственный непроверенный вживую код проекта. **Делай по порядку: сначала 1, убедись что работает, потом 2.**

---

## Как это устроено (прочитай, иначе шаги ниже выглядят произвольными)

**Доска одна на всех.** `~/.hermes/kanban.db` — общая для всех профилей by design, не форкается по профилям.

**Диспетчер ровно один.** Он крутится внутри gateway и раз в минуту смотрит на доску: если появилась готовая задача с исполнителем — запускает `hermes -p <исполнитель>` подпроцессом. Поэтому **одного запущенного gateway достаточно, чтобы работала вся команда** — назначен секретарский (он и так системный сервис).

⚠️ Когда в части 2 появятся ещё шесть gateway (по одному на бота), у них у всех в конфиге стоит `dispatch_in_gateway: false`. Это требование документации самого Hermes: несколько диспетчеров на одну SQLite-базу плодят соединения и дерутся за WAL. Я это уже прописал — просто не убирай.

**Передача работы.** Агент вызывает `kanban_create(title=..., assignee="legal", body="весь контекст")`. Дальше диспетчер поднимает `legal`, тот получает протокол работы с карточкой автоматически (Hermes вшивает его в системный промпт), делает дело и закрывает карточку с итогом. Результат виден в `kanban show` и на вкладке Kanban веб-дашборда (фаза 6).

**Ответ приходит не в чат, а на доску.** Это асинхронный механизм: спросил → агент передал коллеге → сказал тебе, кому передал → результат появился на карточке. Для синхронного «спросил в чате, ответил нужный» — это часть 2.

# Часть 1 — Kanban

## 1.1 Обновить конфиги и персоны

```bash
cd ~/ai-team-v2 && git pull
for p in secretary brain finance tutor tracker research legal; do
  cp profiles/$p/SOUL.md     ~/.hermes/profiles/$p/SOUL.md
  cp profiles/$p/config.yaml ~/.hermes/profiles/$p/config.yaml
done
```

Что изменилось: во всех семи включён тулсет `kanban` (инструменты `kanban_create`/`kanban_show`/`kanban_complete`…), в каждую персону добавлен раздел «Офис» — состав команды и правила передачи. В секретарском конфиге появились лимиты диспетчера, у остальных — `dispatch_in_gateway: false`.

## 1.2 Описать роли — это то, по чему агенты и декомпозер понимают, кто чем занимается

Описания живут в `<профиль>/profile.yaml` и читаются двумя механизмами: декомпозером Kanban (когда большую задачу надо разбить и раздать) и гейтом из части 2. Задаю текстом, а не `--auto`: авто-генерация тратит вызовы LLM и напишет расплывчатее, чем можно сформулировать руками.

```bash
hermes profile describe secretary --text "Время и обязательства Михаила: дедлайны, напоминания, Google Calendar, задачи в Todoist, утренние сводки."
hermes profile describe brain      --text "База знаний Михаила в Obsidian vault: найти и процитировать заметку, дописать новую через Pull Request."
hermes profile describe finance    --text "Личные деньги Михаила: учёт трат и доходов с фриланса, накопления на переезд, планирование бюджета."
hermes profile describe tutor      --text "Самообразование Михаила: математика (матан, линал, дискретка, теорвер), Python, алгоритмы, C++, SQL, машинное обучение. Объясняет, задаёт задачи, проверяет решения."
hermes profile describe tracker    --text "Состояние личных проектов Михаила: на чём остановились, что зависло, какие вопросы остались открытыми."
hermes profile describe research   --text "Ресёрч в интернете по запросу: найти информацию, проверить по нескольким источникам, дать выжимку со ссылками."
hermes profile describe legal      --text "Правовые вопросы фрилансера в России: договоры с заказчиками, самозанятость и ИП, права на результат работы, маркетплейсы."
```

Проверь, что записалось:
```bash
hermes profile describe secretary
hermes profile describe legal
```

## 1.3 Перезапустить диспетчер

```bash
sudo $(which hermes) -p secretary gateway restart
```
(`$(which hermes)` обязательно: gateway секретаря — системный сервис, нужен `sudo`, а `sudo` сбрасывает `PATH`.)

## 1.4 Тест — ручная задача

⚠️ **Команды доски запускай с `-p secretary`.** Доска общая, и без `-p` задача создастся та же самая — но проверка «а есть ли живой диспетчер» смотрит на профиль, из-под которого ты выполняешь команду. Без `-p secretary` она проверит дефолтный профиль, у которого gateway нет, и напугает тебя ложным предупреждением.

```bash
hermes -p secretary kanban create "Найди актуальные лимиты по самозанятости на 2026 год" --assignee legal
```
Если диспетчер на месте, команда об этом скажет (`gateway pid=…, dispatch enabled`). Если ругнётся, что gateway не запущен, — вернись к шагу 1.3.

```bash
hermes -p secretary kanban list
```
Подожди до минуты (тик диспетчера) и посмотри снова — статус должен уехать в `running`, потом в `done`. Результат:
```bash
hermes -p secretary kanban show <id-задачи>
```
Внизу карточки должен быть `summary` от юриста.

## 1.5 Тест — то, ради чего всё: передача между агентами

В чате с секретарём:
```bash
hermes -p secretary
```
```
Мне нужно понять, могу ли я как самозанятый работать с иностранным заказчиком. Разберись.
```

Ожидаемо: секретарь **не отвечает сам** (это не его зона), а создаёт карточку для `legal`, говорит тебе, что передал, и называет кому. Через минуту юрист отрабатывает, результат — на доске:
```bash
hermes -p secretary kanban list
hermes -p secretary kanban show <id>
```

Если секретарь ответил сам или сказал «это не ко мне» без передачи — пришли мне его ответ, поправлю формулировку в персоне.

## 1.6 На что смотреть

- **Не гоняют ли агенты друг друга по мелочам.** Каждая карточка = отдельный запуск агента = деньги. Если секретарь передаёт то, что мог сказать сам, — ужесточим правило в персоне.
- **Хватает ли контекста в карточке.** Исполнитель не видит твой разговор. Если он переспрашивает очевидное или уходит не туда — значит `body` пишется бедно, это правится в персоне.
- **Лимиты.** В секретарском конфиге стоит «не больше 2 агентов одновременно, и не больше 1 экземпляра каждой роли». Если увидишь, что задачи копятся слишком долго, — поднимем.

# Часть 2 — Общий чат в Telegram

⚠️ **Здесь единственный непроверенный вживую код проекта** — плагин `office-gate`. Логика распознавания обращений покрыта тестами (`python3 plugins/office-gate/test_mentions.py`), но поведение классификатора на живых сообщениях предсказать нельзя — его придётся калибровать. Начинай эту часть, только когда часть 1 уже работает.

## 2.1 Завести шесть ботов

Секретарский бот уже есть. Для остальных: @BotFather → `/newbot` на каждого (`brain`, `finance`, `tutor`, `tracker`, `research`, `legal`). Имена любые, главное — не перепутать, какой токен чей.

Токены — сразу в `.env` соответствующего профиля, руками на сервере:
```bash
echo 'TELEGRAM_BOT_TOKEN=<токен бота brain>' >> ~/.hermes/profiles/brain/.env
# …и так для каждого из шести
chmod 600 ~/.hermes/profiles/*/.env
```

## 2.2 Создать группу и узнать её ID

Создай в Telegram группу, добавь туда **себя и всех семь ботов**. В настройках группы отключи ботам privacy mode или дай им админку — иначе бот не видит обычные сообщения (BotFather → `/setprivacy` → Disable для каждого бота; проще выдать всем ботам админа в группе).

ID группы: напиши что-нибудь в группу и посмотри
```bash
tail -50 ~/.hermes/profiles/secretary/logs/gateway.log | grep -i chat
```
ID группы отрицательный, вида `-1001234567890`.

## 2.3 Разрешить группу всем профилям

```bash
for p in secretary brain finance tutor tracker research legal; do
  echo 'TELEGRAM_GROUP_ALLOWED_CHATS=<ID группы>' >> ~/.hermes/profiles/$p/.env
done
```
(Эта переменная авторизует всех участников указанного чата — подтверждено по исходникам gateway.)

## 2.4 Поставить гейт на все семь профилей

```bash
cd ~/ai-team-v2 && git pull
for p in secretary brain finance tutor tracker research legal; do
  mkdir -p ~/.hermes/profiles/$p/plugins
  cp -r plugins/office-gate ~/.hermes/profiles/$p/plugins/
  hermes -p $p plugins enable office-gate
done
```

## 2.5 Поднять gateway каждому агенту

Секретарский уже работает. Остальным шести:
```bash
for p in brain finance tutor tracker research legal; do
  hermes -p $p gateway setup    # выбрать Telegram, вставить токен, allowlist = твой Telegram id
  hermes -p $p gateway start
done
```
`gateway setup` — мастер, он задаёт вопросы, поэтому в цикле встанет на первом же. Прогони по одному.

Проверь, что все живы:
```bash
for p in secretary brain finance tutor tracker research legal; do
  echo -n "$p: "; hermes -p $p gateway status | head -1
done
```

## 2.6 Калибровка — вот тут начинается настоящая работа

Проверяй по очереди, в группе:

1. **«секретарь, поставь напоминание на пятницу»** → отвечает только секретарь. Обращение по имени распознаётся без вызова модели, включая склонения («секретарю», «секретарём»).
2. **«юрист, глянь оферту»** → только юрист. Остальные молчат, тоже без вызова модели — упоминание чужого имени для них стоп-сигнал.
3. **«что там у меня по деньгам за неделю»** → без имени. Тут работает классификатор: должен отозваться финансист, остальные промолчать.
4. **«привет, как дела»** → в идеале молчат все или отвечает один. Если ответили трое — классификатор слишком мягкий, скажи мне.
5. **Ответь реплаем на сообщение любого агента** → отвечает именно он, разговор продолжается.
6. **Главная проверка: не пропало ли сообщение.** Если на явно адресованный вопрос не ответил НИКТО — это худший сценарий, сообщи сразу. Плагин спроектирован так, чтобы при любой ошибке пропускать, а не молчать, но живой классификатор может ошибаться.

**Пришли мне 5-10 реальных примеров** (сообщение → кто ответил → кто должен был). По ним я поправлю промпт классификатора или список имён — это ожидаемая часть работы, а не признак поломки.

## 2.7 Известные слабые места — честно, заранее

- **Классификатор видит только описание роли**, то есть одну строку из `profile.yaml`. Чем точнее описание из шага 1.2, тем лучше решения. Если агент систематически лезет не в свои темы — начинать надо с правки описания.
- **Могут ответить двое** на пограничное сообщение. Каждый решает за себя, общего арбитра нет по дизайну («без куратора» из брифа). Если будет раздражать — добавим правило «отвечает один», но это уже потребует общего состояния между процессами.
- **Стоимость.** Сообщение без имени = по одному дешёвому классифицирующему вызову у каждого из семи агентов. Копейки, но не ноль. Обращение по имени бесплатно — привыкнешь звать по имени, и расход почти исчезнет.
- **Семь gateway-процессов** на сервере. Памяти хватает с запасом, но это семь фоновых процессов вместо одного.

## Критерии готовности фазы 5
- [ ] Задача с доски подхватывается назначенным агентом без ручного вмешательства.
- [ ] Агент передаёт чужую тему коллеге сам и говорит, кому передал.
- [ ] В карточке хватает контекста, чтобы исполнитель понял задачу, не видя разговора.
- [ ] В группе на обращение по имени отвечает именно тот агент.
- [ ] Сообщения не пропадают: не бывает так, что не ответил никто.
- [ ] Диспетчер ровно один (у остальных gateway `dispatch_in_gateway: false`).
