# Фаза 5 — Runbook: офис (агенты видят друг друга)

**Цель:** семь агентов работают как команда. Задачу, которая не по адресу, агент передаёт коллеге сам, без куратора. В общем чате отвечает тот, кому тема ближе.

Это **две независимые части**. Часть 1 (Kanban) — готовая функция Hermes, ничего от тебя не требует кроме конфигов, и работает вживую. Часть 2 (общий чат) требует шесть новых ботов и содержит единственный написанный нами код. **Делай по порядку: сначала 1, убедись что работает, потом 2.**

> **Статус части 2:** первый живой прогон провалился — на каждое сообщение отвечали все семь агентов и заводили дубли карточек. Причина и разбор — во вводной к части 2. Плагин переписан (v3, арбитр вместо семи независимых решений), настройки поправлены, но **заново вживую ещё не проверен**.

---

## Как это устроено (прочитай, иначе шаги ниже выглядят произвольными)

**Доска одна на всех.** `~/.hermes/kanban.db` — общая для всех профилей by design, не форкается по профилям.

**Диспетчер ровно один.** Он крутится внутри gateway и раз в минуту смотрит на доску: если появилась готовая задача с исполнителем — запускает `hermes -p <исполнитель>` подпроцессом. Поэтому **одного запущенного gateway достаточно, чтобы работала вся команда** — назначен секретарский (он и так системный сервис).

⚠️ Когда в части 2 появятся ещё шесть gateway (по одному на бота), у них у всех в конфиге стоит `dispatch_in_gateway: false`. Это требование документации самого Hermes: несколько диспетчеров на одну SQLite-базу плодят соединения и дерутся за WAL. Я это уже прописал — просто не убирай.

**Передача работы.** Агент вызывает `kanban_create(title=..., assignee="legal", body="весь контекст")`. Дальше диспетчер поднимает `legal`, тот получает протокол работы с карточкой автоматически (Hermes вшивает его в системный промпт), делает дело и закрывает карточку с итогом. Результат виден в `kanban show` и на вкладке Kanban веб-дашборда (фаза 6).

**Ответ приходит не в чат, а на доску.** Это асинхронный механизм: спросил → агент передал коллеге → сказал тебе, кому передал → результат появился на карточке. Для синхронного «спросил в чате, ответил нужный» — это часть 2.

# Часть 1 — Kanban

## 1.1 Обновить конфиги и персоны

```bash
cd ~/ai-team-v2 && git pull
for p in secretary brain finance tutor tracker research legal; do
  cp profiles/$p/SOUL.md     ~/.hermes/profiles/$p/SOUL.md
  cp profiles/$p/config.yaml ~/.hermes/profiles/$p/config.yaml
done
```

Что изменилось: во всех семи включён тулсет `kanban` (инструменты `kanban_create`/`kanban_show`/`kanban_complete`…), в каждую персону добавлен раздел «Офис» — состав команды и правила передачи. В секретарском конфиге появились лимиты диспетчера, у остальных — `dispatch_in_gateway: false`.

⚠️ **Подводный камень, на котором мы уже споткнулись.** Убрать `kanban` из `disabled_toolsets` — **недостаточно**. Инструменты `kanban_*` появляются в сессии, только если профиль дополнительно перечислил `kanban` в верхнеуровневом ключе `toolsets`. Без этого агент видит `kanban` в списке тулсетов при старте, но вызвать `kanban_create` не может: на первом живом прогоне секретарь честно не нашёл инструмент и полез обходить через терминал (получилось, но только потому, что терминал у него есть — у пяти лёгких ролей его нет, они бы просто не смогли передать задачу). Обе строки уже проставлены в конфигах, просто знай, почему их две.

**Проверка, что тулы реально доехали:**
```bash
hermes -p legal
```
```
какие kanban-инструменты тебе доступны?
```
Должен перечислить `kanban_create`, `kanban_show`, `kanban_list` и т.д. Если говорит, что их нет, — конфиг не скопировался или профиль не перезапущен.

## 1.2 Описать роли — это то, по чему агенты и декомпозер понимают, кто чем занимается

Описания живут в `<профиль>/profile.yaml` и читаются двумя механизмами: декомпозером Kanban (когда большую задачу надо разбить и раздать) и гейтом из части 2. Задаю текстом, а не `--auto`: авто-генерация тратит вызовы LLM и напишет расплывчатее, чем можно сформулировать руками.

```bash
hermes profile describe secretary --text "Время и обязательства Михаила: дедлайны, напоминания, Google Calendar, задачи в Todoist, утренние сводки."
hermes profile describe brain      --text "База знаний Михаила в Obsidian vault: найти и процитировать заметку, дописать новую через Pull Request."
hermes profile describe finance    --text "Личные деньги Михаила: учёт трат и доходов с фриланса, накопления на переезд, планирование бюджета."
hermes profile describe tutor      --text "Самообразование Михаила: математика (матан, линал, дискретка, теорвер), Python, алгоритмы, C++, SQL, машинное обучение. Объясняет, задаёт задачи, проверяет решения."
hermes profile describe tracker    --text "Состояние личных проектов Михаила: на чём остановились, что зависло, какие вопросы остались открытыми."
hermes profile describe research   --text "Ресёрч в интернете по запросу: найти информацию, проверить по нескольким источникам, дать выжимку со ссылками."
hermes profile describe legal      --text "Правовые вопросы фрилансера в России: договоры с заказчиками, самозанятость и ИП, права на результат работы, маркетплейсы."
```

Проверь, что записалось:
```bash
hermes profile describe secretary
hermes profile describe legal
```

## 1.3 Перезапустить диспетчер

```bash
sudo $(which hermes) -p secretary gateway restart
```
(`$(which hermes)` обязательно: gateway секретаря — системный сервис, нужен `sudo`, а `sudo` сбрасывает `PATH`.)

## 1.4 Тест — ручная задача

⚠️ **Команды доски запускай с `-p secretary`.** Доска общая, и без `-p` задача создастся та же самая — но проверка «а есть ли живой диспетчер» смотрит на профиль, из-под которого ты выполняешь команду. Без `-p secretary` она проверит дефолтный профиль, у которого gateway нет, и напугает тебя ложным предупреждением.

```bash
hermes -p secretary kanban create "Найди актуальные лимиты по самозанятости на 2026 год" --assignee legal
```
Если диспетчер на месте, команда об этом скажет (`gateway pid=…, dispatch enabled`). Если ругнётся, что gateway не запущен, — вернись к шагу 1.3.

```bash
hermes -p secretary kanban list
```
Подожди до минуты (тик диспетчера) и посмотри снова — статус должен уехать в `running`, потом в `done`. Результат:
```bash
hermes -p secretary kanban show <id-задачи>
```
Внизу карточки должен быть `summary` от юриста.

## 1.5 Тест — то, ради чего всё: передача между агентами

В чате с секретарём:
```bash
hermes -p secretary
```
```
Мне нужно понять, могу ли я как самозанятый работать с иностранным заказчиком. Разберись.
```

Ожидаемо: секретарь **не отвечает сам** (это не его зона), а создаёт карточку для `legal`, говорит тебе, что передал, и называет кому. Через минуту юрист отрабатывает, результат — на доске:
```bash
hermes -p secretary kanban list
hermes -p secretary kanban show <id>
```

Если секретарь ответил сам или сказал «это не ко мне» без передачи — пришли мне его ответ, поправлю формулировку в персоне.

## 1.6 На что смотреть

- **Не гоняют ли агенты друг друга по мелочам.** Каждая карточка = отдельный запуск агента = деньги. Если секретарь передаёт то, что мог сказать сам, — ужесточим правило в персоне.
- **Хватает ли контекста в карточке.** Исполнитель не видит твой разговор. Если он переспрашивает очевидное или уходит не туда — значит `body` пишется бедно, это правится в персоне.
- **Лимиты.** В секретарском конфиге стоит «не больше 2 агентов одновременно, и не больше 1 экземпляра каждой роли». Если увидишь, что задачи копятся слишком долго, — поднимем.

# Часть 2 — Общий чат в Telegram

Здесь живёт `office-gate` — единственный написанный нами код в проекте. **Версия 3.** Версия 2 провалилась на живом прогоне, и провал был архитектурный, а не «плохой промпт»: каждый из семи агентов решал за себя, «моя ли это тема». При недоступном классификаторе хук пропускал сообщение (чтобы никто не молчал) — и на одну фразу отвечали ВСЕ СЕМЬ, а каждый из них ещё и заводил свою карточку одному и тому же исполнителю. Пять дублей финансисту, четыре мозгу, каждая карточка — отдельный платный запуск.

Вывод, который стоит запомнить: **при независимом решении семи процессов «отвечает ровно один» недостижимо в принципе**, каким бы хорошим ни был классификатор. Поэтому в v3 решение принимается один раз на сообщение.

## Как v3 решает, кто отвечает

Сверху вниз, первое совпадение выигрывает:

| Что в сообщении | Кто отвечает | Модель вызывается? |
|---|---|---|
| Личка боту | этот бот | нет |
| Реплай на сообщение агента | он же | нет |
| `/команда@имя_бота` | только названный бот | нет |
| Названо имя роли («юрист», «секретарю», «мозг») | только он | нет |
| Названо чужое имя | остальные молчат | нет |
| Имени нет | решает арбитр | да, **один раз на всех** |

**Арбитр.** Все семь процессов видят одно сообщение и атомарно борются за право решить (`INSERT OR IGNORE` в общую `~/.hermes/office-routing.db`). Победитель делает один вызов модели, показав ей **весь состав команды с описаниями ролей**, и просит выбрать ровно одного. Решение пишется в ту же строку, остальные шестеро его читают и молчат, если названы не они.

Почему это сильнее семи независимых «да/нет»: ровно один отвечающий гарантирован механикой, а не удачей; вызовов модели в семь раз меньше; и модель выбирает **из списка**, а не гадает вслепую, не зная, кто ещё есть в команде.

**Если что-то сломалось** (нет ключа, модель недоступна, таймаут) — отвечает дежурный профиль, по умолчанию секретарь. Это сознательная смена политики v2: раньше сбой означал «отвечают все» (шум и деньги), теперь — «отвечает один, и он умеет передать работу дальше». Молчания не возникает ни в одном случае.

## Как результат попадает в чат

Сырые уведомления доски (`✔ [default] @finance Kanban t_xxx done — …`) **выключены** (`auto_subscribe_on_create: false`). Они приходили ботом-диспетчера сухим системным текстом, а следом секретарь пересказывал то же своими словами — двойное сообщение на каждую карточку.

Вместо этого исполнитель отчитывается сам: плагин регистрирует инструмент `office_report`, который пишет в группу **ботом самого исполнителя**. В персонах всех семи прописано: закончил карточку — скажи в чат, от кого была задача, в чём она была и что вышло. В группе это выглядит как живая передача работы:

> **Секретарь:** Вопрос по НДС — не моя зона, передал юристу.
> **Юрист:** Михаил, от секретаря прилетел вопрос про НДС для самозанятого. НПД освобождает от НДС полностью, счета выставляешь без него.

⚠️ Цена решения, честно: если исполнитель забудет позвать `office_report`, результат останется только на доске (`hermes -p secretary kanban show <id>`). Инструкция в персоне есть, но это инструкция модели, а не техническая гарантия. Если увидишь, что карточки закрываются молча — скажи, вернём авто-уведомления как страховку.

## 2.1 Завести шесть ботов

Секретарский бот уже есть. Для остальных: @BotFather → `/newbot` на каждого (`brain`, `finance`, `tutor`, `tracker`, `research`, `legal`). Токены — сразу в `.env` соответствующего профиля, руками на сервере:
```bash
echo 'TELEGRAM_BOT_TOKEN=<токен бота brain>' >> ~/.hermes/profiles/brain/.env
# …и так для каждого из шести
chmod 600 ~/.hermes/profiles/*/.env
```

⚠️ **В настройках каждого бота (BotFather → Bot Settings) есть два тумблера из Bot API 10.0 (май 2026) — оба держи выключенными:**
- **Secretary Mode** — несмотря на название, это не про нашего агента-секретаря. Это Business Mode: даёт боту подключаться к личному аккаунту и писать/читать от твоего имени во всех твоих чатах. Не нужно.
- **Bot to Bot Communication Mode** — разрешает боту видеть сообщения других ботов. У нас в группе семь ботов; включишь — рискуешь бесконечным циклом (прямое предупреждение Telegram). Не нужно: работу агенты передают через доску, а отчитываются через `office_report`. Выключенный тумблер заодно гарантирует, что агенты не начнут реагировать на отчёты друг друга.

Это НЕ то же самое, что `/setprivacy` из шага 2.2 — тот остаётся **Disable**, он про то, видит ли бот обычные сообщения людей.

## 2.2 Создать группу и узнать её ID

Создай группу, добавь себя и всех семь ботов. Каждому боту через BotFather → `/setprivacy` → **Disable**, иначе бот не увидит обычные сообщения.

ID группы: напиши что-нибудь в группу и посмотри
```bash
tail -50 ~/.hermes/profiles/secretary/logs/gateway.log | grep -i chat
```
ID отрицательный, вида `-1001234567890`.

## 2.3 Прописать окружение всем семи профилям

```bash
GROUP=-1001234567890          # ← подставь свой ID

for p in secretary brain finance tutor tracker research legal; do
  {
    echo "TELEGRAM_GROUP_ALLOWED_CHATS=$GROUP"
    echo "OFFICE_GROUP_CHAT_ID=$GROUP"
    echo "OFFICE_DEFAULT_RESPONDER=secretary"
  } >> ~/.hermes/profiles/$p/.env
done
```

Что это за переменные:
- `TELEGRAM_GROUP_ALLOWED_CHATS` — авторизует всех участников чата (штатная переменная Hermes).
- `OFFICE_GROUP_CHAT_ID` — куда `office_report` шлёт отчёт исполнителя.
- `OFFICE_DEFAULT_RESPONDER` — кто отвечает, когда арбитр не смог решить.

Отдельно каждому профилю — **username его бота**, чтобы служебные команды вида `/sethome@legalllmbot` обрабатывал только адресат (без этого на одну команду реагировали все семеро):
```bash
echo 'OFFICE_BOT_USERNAME=legalllmbot' >> ~/.hermes/profiles/legal/.env
# …и так для каждого, без символа @
```

## 2.4 Поставить гейт на все семь профилей

```bash
cd ~/ai-team-v2 && git pull
for p in secretary brain finance tutor tracker research legal; do
  cp profiles/$p/SOUL.md     ~/.hermes/profiles/$p/SOUL.md
  cp profiles/$p/config.yaml ~/.hermes/profiles/$p/config.yaml
  mkdir -p ~/.hermes/profiles/$p/plugins
  rm -rf  ~/.hermes/profiles/$p/plugins/office-gate
  cp -r plugins/office-gate ~/.hermes/profiles/$p/plugins/
  hermes -p $p plugins enable office-gate
done
```

Прогони тесты гейта — они проверяют ровно то, что сломалось вживую:
```bash
python3 ~/ai-team-v2/plugins/office-gate/test_mentions.py
```
Должно вывести `OK — все проверки прошли`.

## 2.5 Перезапустить ВСЕ gateway — включая секретаря

⚠️ **Это тот шаг, на котором в прошлый раз всё сломалось.** Плагины читаются при старте процесса: `plugins enable` без рестарта не даёт ничего. Секретарский gateway работал с 06:38, плагин скопировали позже — и у секретаря гейта просто не было. Отсюда его ответы на всё подряд, включая адресованное юристу.

```bash
sudo $(which hermes) -p secretary gateway restart    # системный сервис, нужен sudo
for p in brain finance tutor tracker research legal; do

done
```

Проверь, что все семь живы (`BrokenPipeError` от `head` игнорируй, это косметика):
```bash
for p in secretary brain finance tutor tracker research legal; do
  echo -n "$p: "; hermes -p $p gateway status | head -1
done
```

## 2.6 Калибровка

Проверяй по очереди, в группе. **Главное, что проверяем: на каждое сообщение отвечает ровно один.**

1. **«секретарь, поставь напоминание на пятницу»** → только секретарь.
2. **«юрист, какой ндс щас?»** → только юрист. Секретарь молчит — в прошлый раз он влезал именно сюда.
3. **«что там у меня по деньгам за неделю»** (без имени) → решает арбитр, отвечает один (ожидаемо финансист).
4. **«привет, как дела»** → отвечает один (ожидаемо секретарь как дежурный).
5. **Реплай на сообщение любого агента** → отвечает он же.
6. **Передача работы:** попроси секретаря то, что не его (например правовой вопрос) → секретарь одной строкой говорит, кому передал, и через минуту **исполнитель сам пишет в чат** от своего имени: от кого задача и результат. Ни системных `✔ Kanban … done`, ни пересказа секретаря быть не должно.
7. **Проверь доску на дубли:** `hermes -p secretary kanban list` — на один твой вопрос должна быть **одна** карточка, не пять.

Если что-то из этого не так — пришли конкретно: сообщение, кто ответил, кто должен был.

## 2.7 Известные слабые места — честно

- **Арбитр может ошибиться в выборе.** Он видит только описания ролей из `profile.yaml` (шаг 1.2). Систематически мажет — правь описание, а не промпт.
- **Ожидание решения блокирует свой gateway** (хуки Hermes синхронные). Бюджет ожидания — 6 секунд, дальше фолбэк на дежурного. На практике решение приходит за ~1 секунду, но если увидишь подтормаживания у ботов — скажи, вынесу решение в фон.
- **`office_report` — инструкция модели, а не гарантия.** См. врезку выше про молча закрытые карточки.
- **Семь gateway-процессов** на сервере вместо одного.
- **Bot to Bot Communication Mode выключен намеренно** (см. 2.1). Если когда-нибудь захочется, чтобы агенты буквально переписывались друг с другом — это отдельная фича с защитой от циклов, не делать походя.

- [ ] В группе на обращение по имени отвечает именно тот агент.
- [ ] **На любое сообщение в группе отвечает ровно один агент** — ни ноля, ни семи.
- [ ] На один вопрос заводится одна карточка, а не по одной от каждого агента.
- [ ] Исполнитель сам пишет в чат от своего имени: от кого задача и что вышло.
- [ ] Диспетчер ровно один (у остальных gateway `dispatch_in_gateway: false`).

## Приложение — почему в конфигах четыре разных места про инструменты

Это не дублирование, у каждого своя роль. Каждую строку таблицы мы узнали на живой поломке, поэтому фиксирую:

| Ключ | Что делает | Что будет без него |
|---|---|---|
| `agent.disabled_toolsets` | **вычитает** тулсеты | лишние инструменты в контексте |
| `toolsets: [hermes-cli, kanban]` | **opt-in** в оркестраторский режим Kanban | тулсет числится включённым, но `kanban_create` вызвать нельзя |
| `platform_toolsets.cli` | явный список для терминала **и воркеров Kanban** | обычная сессия и Kanban-воркер получают разные наборы |
| `platform_toolsets.telegram` | явный список для сессий из чата | в чате агент беднее, чем в терминале |

Два последних коварнее всего, и оба выстрелили по очереди.

**Про `cli`.** Диспетчер запускает исполнителя с жёстким пином `--toolsets`, вычисляя список из конфига. Пока список выводился неявно из композита `hermes-cli`, у ресёрчера в обычном чате веб-поиск был, а у него же в роли воркера — нет: задача вставала с «нет инструментов для веб-поиска».

**Про `telegram`.** Hermes резолвит набор по имени площадки — `platform_toolsets.get(platform)` в `hermes_cli/tools_config.py`. Мы прописали только `cli`, и сессии из группового чата откатывались на дефолтный композит `hermes-telegram`: юрист в чате честно сказал «у меня нет веб-инструмента», хотя в терминале веб у него есть. Держи оба списка одинаковыми — агент должен быть одним и тем же человеком в чате и в работе.

**Как проверять после правок конфига** — сравни два набора, они должны совпадать:
```bash
# обычная сессия: строка "toolsets:" в шапке
hermes -p research

# роль воркера: создай задачу и посмотри, чем она кончилась
hermes -p secretary kanban create "Проверка веб-доступа: найди ставку НПД и дай ссылку" --assignee research
hermes -p secretary kanban list
```
